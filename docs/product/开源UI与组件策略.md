# 开源 UI 与组件策略：能不能做出好组件？要不要自创？

> 关联：D2 产品定位、D3 阶段 3–4。  
> 读者：产品决策；不要求会写代码也能看懂。

---

## 先纠正一个常见误解

**「不走商业 = 什么开源协议都能随便用」——不完全对。**

| 许可类型 | 代表 | 个人/开源/甚至将来商业化 |
|----------|------|--------------------------|
| 宽松 | MIT、Apache-2.0、BSD、ISC | 通常可商用、可再分发（保留声明） |
| 弱传染 | LGPL | 修改库本身需开源；你单独的应用一般可闭源 |
| 强传染 | GPL / AGPL | 衍生作品常需同协议开源；网络服务要特别看 AGPL |
| 创作共享 NC | 部分素材站 | **禁止商业用途**；项目变大、接赞助、卖服务都可能踩线 |
| 设计系统「皮肤」 | 多数规范 | 规范/理念通常可学；**别原样搬官方品牌资产** |

对我们的含义：

1. **宽许可证（MIT/Apache）优先**——现在是开源，以后也可能接赞助、做托管版；一开始就选干净的，省得洗协议。  
2. **「不走商业」降低的是动机顾虑，不是法律关卡**——真正要盯的是 NC（非商业）和品牌素材。  
3. **可以自创**：设计风格可以借鉴 Material、Ant 的「做法」，不必、也不应直接抄品牌名与官方 Logo 组件源码里带商标的部分。

## 组件从哪来？四条腿走路

### 腿 1：底座已有的 M3 组件（立刻有）

m3e-canvas 已有一整套语义组件：按钮、FAB、顶栏、导航、列表、对话框、表单控件等，**Apache-2.0 体系 + 项目自身 MIT**。

这是阶段 0–2 就能交付「看起来专业」的本钱。

### 腿 2：整合成熟开源设计系统（阶段 3–4）

| 系统 | 许可倾向 | 适合放进产品的方式 |
|------|----------|--------------------|
| Material 3 | Apache-2.0 | 已有；继续作为默认 Pack |
| shadcn/ui | MIT | 组件源码进用户项目；我们做预览与导出描述 |
| Radix | MIT | 无样式行为组件参考 |
| Tabler Icons / Lucide / Heroicons | MIT / MIT / MIT | 图标库第一批 |
| Ant Design | MIT | 国内 Pack；注意品牌名在提示词中的表述 |
| Element Plus | MIT | 国内 Pack 候选 |

**做法：** 不整包拷贝进画布运行时，而是：

1. 抽「语义 → 各系统视觉规则」  
2. 我们画布用**统一模型**渲染预览  
3. 导出时按目标系统生成提示词/代码描述  

这样版权面更清晰，也符合「一套设计多套输出」。

### 腿 3：自创组件与视觉变体（真正的差异）

**能自创，而且应该自创一部分。** 原因：

- 纯拼盘没有记忆点  
- 自创「中性、可换肤」的组件，才能同时服务 Material / shadcn / Ant  
- 开源社区愿意来，是因为有辨识度、可扩展，不是又一个图标站  

自创建议集中在：

1. **产品自己的组件语言**：连接组、流程箭头、资源卡片、模板卡片  
2. **视觉变体**：同一语义组件的不同观感（圆角尺度、密度、品牌色）  
3. **缺失补全**：底座没有但高频的（例如空状态、步骤条、分段控件、日期选择占位等）——按数据模型 `Kind` 扩展，而不是堆 CSS  

### 腿 4：社区贡献（开源软件的增长飞轮）

- 明确「如何加一个组件 / 一个 Pack / 一个图标源」的文档  
- 模板与主题可 PR  
- 保留原作者致谢与 NOTICE，建立合规与信任

## 「做得好」的双标准：体验好 + 产出好

用户愿意留下来的，从来不是功能列表，而是：

> **用得顺手（过程）× 做出来的东西能用（结果）**

### A. 使用体验好（过程）

| 原则 | 落到产品上 |
|------|------------|
| 30 秒内有反馈 | 打开就能拖组件；空状态给「从模板开始 / 让 AI 画一个」 |
| 少选项、多默认 | 默认主题、默认 16dp 网格、默认手机框；高级项收进面板 |
| 所见即所得 | 切换设计系统时画布立刻变，不要「保存后才生效」 |
| AI 不抢戏 | AI 改完可撤销；能看见「AI 动了哪些」 |
| 存得下、找得到 | 项目列表像对话记录；本地文件；一键打开上次 |
| 不吓唬非设计师 | 术语用日常中文（按钮/顶栏），不甩 M3 黑话当门槛 |

### B. 做出来的东西好（结果）

这是开源画布工具最容易做差的地方——画布热闹，导出很烂。

| 原则 | 落到产品上 |
|------|------------|
| 组件默认就好看 | 默认值按设计系统规范调，不是随便灰按钮 |
| 结构合法 | 磁吸、对齐、边距预设贴近真实布局习惯 |
| 导出即开工 | 提示词包含：布局、层级、交互、主题、技术栈，少让 AI 瞎猜 |
| 多系统不崩 | 换 Pack 后布局仍稳；语义不变、皮变 |
| 可预览可演示 | 点击跳转、返回、滑动，方便向别人讲清楚产品 |
| 资源即用 | 图标拖进画布；模板一键改文案；不是「只能看的画廊」 |

### C. 「结果好」的验收句（可当内部标准）

1. **给 AI 的提示词**：贴进 Claude Code / v0 类工具，第一版不面目全非。  
2. **给人的预览**：外行也能看懂页面在干嘛。  
3. **给开发的结构**：有经验的人按提示词能落地，不用重问。  
4. **给设计系统的出口**：Material 与 shadcn 描述能各自成立。

## 建议的内容与质量策略

```
        优质默认（我们调好）
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
  开源整合   自创扩展   社区 PR
 (Apache/MIT) (我们定义) (有规范)
    │         │         │
    └─────────┴─────────┘
              ▼
     统一语义模型 + 严格默认值
              ▼
     预览好看 + 导出能开工
```

### 短期（阶段 0–2）质量重点

- **不追组件数量**，追「10 个高频组件的默认颜值」  
- 主题面板保证一键好看（预设色板已经很像样，继续打磨）  
- AI 操作的成功率优先于花哨功能  

### 中期（阶段 3–5）

- 图标搜索体验做成「秒搜、秒拖」  
- Pack 切换的视觉可信度（像不像 shadcn，而不只是换个按钮颜色）  
- 模板质量 > 模板数量：少而精的 8–12 个模板  

### 长期

- 社区 Pack / 模板生态  
- 与更多 AI 工具的一键配置（配置片段生成）

## 许可证与合规（产品要开源也认真做）

| 素材/代码 | 策略 |
|-----------|------|
| 基座 m3e-canvas | 保留 MIT 与原作者致谢 |
| Material 相关 | Apache-2.0，NOTICE |
| 图标 | 选 MIT/Apache；每个图标库保留 LICENSE |
| 自创组件与文档 | 建议项目本体 **MIT 或 Apache-2.0**（商业友好，利于采用） |
| 避免 | 来源不明的付费 UI Kit 私货；NC 素材；他人品牌 Logo 当官方组件 |

**建议：** 产品本体用宽松协议，对「将来是否商业化」保持开放；这比「因为不赚钱所以随便用」稳得多。

## 对「能不能做出好组件」的直接回答

| 问题 | 回答 |
|------|------|
| 用开源 UI 能做出好组件吗？ | **能。** 底座已有一套；再系统整合 Lucide/shadcn/Ant，并严控默认值。 |
| 能自创吗？ | **能，而且要创。** 创语义扩展、视觉变体、产品自己的组件与模板语言。 |
| 不走商业是不是更自由？ | 宽松协议本来就自由；**不要拿「非商业」当挡箭牌用 NC 素材**。 |
| 怎样让用户更愿意用？ | **过程顺（少学习、AI 可控、本地项目）+ 结果好（预览像样、导出能开工）。** |

## 下一步与讨论衔接

本策略不推翻 D3 阶段，而是约束阶段 3–5 的质量标准：

- 阶段 3 资源库：质量指标 = 秒搜秒拖 + 默认颜值  
- 阶段 4 Pack：质量指标 = 换皮后「像那个系统」+ 布局不崩  
- 阶段 5 导出：质量指标 = 四条「结果好」验收句  

**建议下一决策点：** 产品命名 → 然后冻结阶段 0 范围并开始动手。
