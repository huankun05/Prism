# 调研：AI 操作 UI 画布 · 同类产品 · 可借鉴方案

> 调研日期：2026 年  
> 背景：基于 m3e-canvas 二次开发，目标是「可编辑的 UI 画布 + 开源资源库」，并希望其他 AI 工具能直接操作画布写 UI，人能实时看到结果。  
> 使用方式：本文档给决策用，不必一次读完；优先看「四、结论」和「五、对我们的建议」。

---

## 一、先回答核心问题：能不能让 AI 操作我们的画布、实时看结果？

**能，而且技术上已经成熟，有多条可选路径。**

这件事的本质是：**把画布暴露成一套「可被程序调用的操作接口」**，AI 工具通过接口改数据，画布监听数据变化自动重绘。

```
用户在 AI 工具里说话
        ↓
AI 理解意图 → 调用画布操作（加按钮、改主题、连页面…）
        ↓
画布数据模型更新（Doc / Item）
        ↓
界面实时重绘（所见即所得）
```

原项目 m3e-canvas **已经有一半答案**：它有完整的 `Doc` JSON 格式，以及 `public/agent.md`——给 AI 编程代理看的说明书。目前的工作流是：

1. AI 生成一份设计 JSON  
2. 生成分享链接（或用户打开 JSON 文件）  
3. 用户在画布里打开、手改  
4. 再复制提示词给编程工具  

这已经是「AI 写 UI」，只是**偏异步、偏一次性**。我们要往前走一步：**同步操作 + 实时看结果**。

## 二、同类产品图谱

按「AI 和 UI 的关系」分四类，我们的产品更接近 **C + 少量 B**。

### A. 提示词 → 代码生成（聊天优先）

| 产品 | 是什么 | 和我们的关系 |
|------|--------|--------------|
| **v0**（Vercel） | 文本/图 → React + shadcn + Tailwind 全栈应用，实时预览、可部署 | 输出终点是代码，不是画布；预览是附带的 |
| **bolt.new** / **Lovable** / **Replit Agent** | 同类：对话生成完整应用 | 重「从 0 写代码」，轻「结构化 UI 编辑」 |
| **Figma Make** | Figma 内用 AI 生成界面 | 生态封闭在 Figma |

**特点**：AI 全权负责，用户大多在聊天框里改，画布感弱。  
**我们不做的**：不做全栈代码沙箱（那是另一条赛道）。

### B. 可视化编辑真代码（设计 ↔ 代码双向）

| 产品 | 是什么 | 可借鉴点 |
|------|--------|----------|
| **Onlook**（开源，约 2.6 万 star） | 「设计师的 Cursor」：在真实 React/DOM 上可视化编辑 + AI 对话改代码 | 代码为 source of truth；iframe 预览 + 元素映射回代码；支持 MCP |
| **Tempo / Builder.io** 等 | 类似：设计器直接改项目代码 | 证明「设计工具和代码打通」有真实需求 |

**特点**：编辑对象是**真实代码仓库**，偏专业前端/设计师。  
**和我们的差异**：我们编辑的是**设计模型**（语义组件），输出才是代码/提示词——更轻、更适合作为「给 AI 的设计中间层」。

### C. 画布 + AI Agent 操作画布（最接近我们）

| 产品/项目 | 是什么 | 可借鉴点 |
|-----------|--------|----------|
| **tldraw Agent Starter Kit**（开源） | 无限画布 SDK + 完整 AI Agent 方案 | Agent 通过**截图 + 结构化形状数据**理解画布；用**类型化 Action** 修改画布；有错误纠正层 |
| **m3e-canvas 自带 agent.md** | AI 代理按文档写设计 JSON，生成分享链接打开 | **最接近我们的底座**：结构化设计模型 + 代理协议 |
| Replit Canvas / 各类 infinite canvas AI | 画布上 AI 生成/修改对象 | 实时协作 + AI 光标 |

tldraw 官方文档明确给出三种 AI 集成模式（对我们的架构设计非常有参考价值）：

1. **画布当输出面**：AI 生成内容，贴到画布上（最简单）  
2. **可视化工作流**：AI 节点串在流程里（过重，暂不需要）  
3. **Agent 直接控制编辑器**：读屏 + 执行类型化 Action（**我们要的**）

Agent 怎么「看」画布（tldraw 做法）：

- 当前视口截图  
- 可见区域的结构化数据  
- 视口外聚类摘要  
- 用户选中项与最近操作  
- 对话历史  

Agent 怎么「改」画布：

- 模型输出符合 schema 的 Action  
- 校验、纠错（修 id、坐标归一化等）  
- 应用到编辑器  

### D. 设计软件的 AI / MCP 插件

| 方案 | 说明 |
|------|------|
| **Figma MCP Server** | 官方/社区有 MCP，让 AI 读写 Figma 文件；说明「设计工具被 AI 操作」已是行业方向 |
| 各类 Figma AI 插件 | 生成/改稿，多在 Figma 体系内闭环 |
| 我们原设想的「Figma 打通」 | 长期价值大，但依赖对方 API/插件生态，适合作为后期出口，不是第一优先 |

## 三、原项目（m3e-canvas）已经给了什么

| 能力 | 现状 | 对「AI 操作画布」的意义 |
|------|------|------------------------|
| 结构化设计模型 `Doc/Item` | 有 | AI 不需要瞎猜像素，操作的是语义对象 |
| `agent.md` 代理协议 | 有（beta） | 已定义 AI 如何生成设计 JSON |
| 分享链接（#docz=压缩 JSON） | 有 | 跨端打开设计的轻量通道 |
| 提示词导出（多语言） | 有 | 设计 → 交给编程工具的出口 |
| 实时 AI 改画布 | **无** | 需要我们加：操作通道 + 监听重绘 |
| 本地项目库 / 文件系统 | **无**（localStorage） | 需要补，否则 AI 和用户难以共享同一份「当前设计」 |
| MCP / 对外工具接口 | **无** | 需要加一层「桥」 |

结论：**语义模型和代理说明书已经具备；缺的是同步通道和本地/跨工具的共享状态。**

## 四、实现「AI 实时操作画布」的三条技术路线

### 路线 1：文件 / 链接交换（现状，异步）

```
AI 写 design.json → 用户打开链接/文件 → 人再改
```

- 优点：零服务器、实现简单、已存在  
- 缺点：不是实时；AI 改不了「你正在编辑的那份」  
- 适合：给外部 AI 编程工具做「初稿生成」

### 路线 2：本地桥接服务（推荐主路径）

```
浏览器画布 ←WebSocket/本地HTTP→ 本地 Bridge ←MCP→ Claude Code / MiMo / Cursor…
```

- 画布启动时连本地 Bridge（或由桌面壳内嵌）  
- AI 通过 MCP 调 Bridge，Bridge 再推给画布  
- 画布实时重绘；也能把当前 Doc 回读给 AI  
- 优点：  
  - 任意 AI 工具（MiMo、Claude Code、Cursor…）都能接  
  - 不依赖把产品改成桌面软件也能做  
  - 和「本地项目文件夹」天然契合：Bridge 也读写同一目录  
- 缺点：需要跑一个小的本地进程（几十 KB～几 MB 级 Node 程序，不是 Electron）

### 路线 3：内嵌 AI + 直接 API（Onlook / v0 风格）

```
产品内聊天框 → 直接调模型 → 立刻改画布
```

- 优点：体验最顺，不依赖外部工具  
- 缺点：用户要配 API Key 或我们出模型成本；和「主要靠 AI 开发、用外部工具」的习惯有重叠  
- 适合：后期增强，不作为唯一路径  

### 推荐组合

| 阶段 | 主路径 |
|------|--------|
| 现在～短期 | **路线 1** 强化（agent.md 协议升级，保证外部 AI 生成的 JSON 更稳） |
| 中期核心 | **路线 2** 本地 Bridge + MCP：外部 AI 实时操作画布 |
| 后期 | **路线 3** 可选内嵌助手 |

**关键判断：桌面壳（Electron/Tauri）不是路线 2 的硬性前提。**  
Bridge 可以是独立 `npx` 小程序；以后若做桌面壳，把 Bridge 打包进去更顺，但先有 Bridge 不必先有壳。

## 五、对我们的建议（可讨论）

### 5.1 产品形态修正

不必在「纯网页」和「Electron」里二选一。更贴合目标的分层是：

1. **画布 Web 应用**（主 UI，来自 m3e-canvas）  
2. **本地数据层**：项目 = 文件夹（design.json + meta）  
3. **本地 Bridge / MCP Server**：让 AI 工具操作「当前打开的设计」  
4. **（可选）桌面壳**：后期用 Tauri 打包，提升安装体验，不是功能必需  

### 5.2 和 Onlook / v0 的定位差异（避免被卷进错误赛道）

| | v0 / Bolt | Onlook | **我们（建议）** |
|--|-----------|--------|------------------|
| 中心 | 生成代码 | 编辑真代码 | **编辑设计模型** |
| AI 输入 | 对话 | 对话 + DOM | 对话 + **MCP/工具** |
| 输出 | 可部署应用 | 真实仓库变更 | **多设计系统提示词/代码 + 可导入模板** |
| 强项 | 快速出应用 | 设计师改生产 UI | **设计作为 AI 可读写的中间层；资源库** |

我们不该和 v0 正面抢「全栈生成」；差异化是：

1. **结构化 UI 设计画布**（可预览流程、可切换设计系统）  
2. **外部 AI 可直接操作画布**（MCP）  
3. **开源 UI/图标/模板资源库**  
4. **设计 → 多套系统提示词**（后续阶段）

### 5.3 最小可行闭环（MVP 建议）

若要验证「AI 实时写 UI」，最小闭环可以是：

1. 画布仍用现有 m3e-canvas  
2. 增加：打开/保存本地项目文件夹  
3. 增加：画布监听「远程操作」（哪怕先是加载完整 JSON 的协议）  
4. 增加：一个极小的 MCP Server  
   - 工具示例：`list_projects` / `read_design` / `write_design` / `add_part`  
5. 在 MiMo 或 Claude Code 里配好 MCP，说一句：「画一个设置页」→ 画布出现设置页  

跑通这一条，产品故事就立住了；后面再做设计系统 Pack、图标库、模板。

## 六、可直接复用/改造的开源参考

| 项目 | 许可 | 借鉴强度 | 用途 |
|------|------|----------|------|
| **m3e-canvas**（基座） | MIT | ★★★★★ | 画布、组件模型、提示词 |
| **tldraw Agent kit** | tldraw 许可（商用需授权；仅参考模式可） | ★★★★ | Agent 看画布、Action 纠错的模式 |
| **Onlook** | Apache-2.0 | ★★★ | 可视化与代码双向、MCP 接入思路 |
| MCP Filesystem / 自建 Server | MIT 等 | ★★★★ | 本地读写与工具暴露方式 |
| Material Symbols 等图标 | Apache-2.0 | ★★★★ | 资源库第一批 |

> 注意：tldraw 商用需要 license，**不要直接依赖其核心 SDK 做产品**，只学习其 Agent 集成模式即可。我们继续以 m3e-canvas（MIT）为底座更干净。

## 七、待你拍板的问题（下一轮讨论）

调研后的下一个问题仍是形态，但选项更清晰了：

**问题：本地能力（项目库 + AI 桥）怎么落地？**

| 选项 | 含义 | 何时到位 |
|------|------|----------|
| **甲** | 纯网页 + 浏览器本地文件夹读写 + 独立 `npx` MCP Bridge | 最快验证「AI 改画布」 |
| **乙** | 第一版就 Tauri 壳，内嵌项目库与 MCP Bridge | 安装体验最好，开发略重 |
| **丙** | 只做网页 + 分享链接，不做本地 Bridge | 最省事，但做不好你说的「本地项目 + 外部 AI 实时操作」 |

**我的倾向仍是甲作为第一阶段**，乙作为明确的第二阶段产品化包装——除非你强烈希望「第一次下载就是安装包软件」。
